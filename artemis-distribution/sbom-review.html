Artemis Distribution SBOM Review

CycloneDX 1.6 — apache-artemis-2.56.0-SNAPSHOT-bin.zip

SBOM Generation Workflow

The distribution SBOM is assembled in four stages across two repositories. Each stage builds on the previous one — npm components from stage 1 propagate through the entire chain via the embedded SBOM merge mechanism.

1
npm SBOM Generation — artemis-console-extension/artemis-extension

@cyclonedx/yarn-plugin-cyclonedx generates a CycloneDX SBOM from the Yarn workspace with full license resolution from node_modules. @cyberstamp/cdx-npm-enrich --prod-only then strips dev-only dependencies by walking package.json dependencies transitively across all workspaces. Result: 263 production npm components with licenses in bom.cdx.json.

2
Console WAR SBOM — artemis-console-war

maven-war-plugin:exploded builds the exploded WAR with Java JARs (hawtio, jolokia, etc.) and the JS frontend. assembly-sbom-maven-plugin:generate scans the exploded directory, identifies each JAR by content-hash matching against the Maven local repository, and merges the npm SBOM from stage 1 via the <externalSboms> parameter. The combined SBOM is packaged into the WAR at META-INF/sbom/bom.cdx.json.

3
Artemis Console WAR SBOM — artemis/artemis-console

This module overlays artemis-console-war, adding Artemis-specific branding and guava, while excluding logging JARs. maven-war-plugin:exploded unpacks the upstream WAR as an overlay — including its META-INF/sbom/bom.cdx.json. The plugin re-scans the modified contents and merges the embedded SBOM it finds inside the overlay. No <externalSboms> is needed: npm components arrive transitively through the embedded SBOM merge. The new SBOM replaces the overlay’s at the same META-INF/sbom/ path.

4
Distribution SBOM — artemis/artemis-distribution

A ContainerDescriptorHandler named "sbom" hooks into maven-assembly-plugin during archive creation. It hashes every file being added to the .tar.gz / .zip, identifies Maven artifacts by content hash, and resolves licenses from effective POMs. When the handler encounters the unpacked console WAR, it merges its embedded SBOM (carrying all npm components through) and strips the original META-INF/sbom/ files from the archive via the isSelected filter. The result is a single merged SBOM covering all 100+ broker JARs, console Java libraries, and npm components.

The librariesOnly SBOM correctly preserves all 409 library components while removing all 81 file components. The dependency graph is clean in both variants — zero orphan entries, zero dangling references.

The npm SBOM is generated by @cyclonedx/yarn-plugin-cyclonedx and enriched by @cyberstamp/cdx-npm-enrich. The yarn plugin produces a complete dependency graph (no missing entries) and resolves licenses for all components. The enrichment tool adds SHA-512 hashes from yarn.lock, strips dev-only components, and adds evidence.identity (manifest-analysis / package-json-analysis) for each production component. Combined with the handler’s Maven identity evidence, all 409 library components have identity evidence — only the 81 file components lack it.

12 nested libraries lack hashes — these are shaded/embedded Maven JARs (e.g., jcip-annotations inside nimbus-jose-jwt, jctools-core inside netty-common) identified via POM analysis rather than content hash.

275 components lack evidence.occurrences (file-path locations): 263 npm packages bundled by webpack into combined JS chunks plus the 12 shaded JARs above. Neither category exists as standalone files in the archive.
